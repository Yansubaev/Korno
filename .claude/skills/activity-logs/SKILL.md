# Логи активности Korno

Источник правды о формате, сообщениях и полях — `docs/debug-logging-guide.md`. Прочитай его целиком до первого запроса к логам: навык говорит, **в каком порядке** читать, гайд — **что** значит каждое поле.

## Шаги

### 1. Найти архивы

Архивы лежат в корне репозитория и в `diagnostics/` (`korno-*.zip`, в `.gitignore`), если пользователь не дал другой путь. Начинай с описи — она склеивает все архивы в один пул без дублей:

```bash
tools/klog/klog.py index                 # корень и diagnostics/
tools/klog/klog.py index путь/к/архивам  # или явные файлы и каталоги
```

Что она показывает и почему имени файла верить нельзя:

- **Источники** — сколько уникальных записей дал каждый архив; `целиком внутри X` — дубль, читать его не нужно. В имени архива стоит сессия **выгрузки**, а не записи; файлы ещё и переименовывают — сессию бери из описи.
- **Сессии** — запуски приложения: сборка из `Log file opened` (`?` — сборка до заголовков), что лежит в общем потоке (`с сэмплами` — старый формат, где подробности записи шли и в общий поток; `каркас` — только `INFO` и выше), причина смерти прошлого процесса.
- **Активности** — `id@дата`: после сноса базы id начинаются заново, и один id бывает у разных записей. Полнота: `full` — есть архив активности, `full(app)` — подробности восстановлены из старого общего потока, `skeleton` — только каркас, нужен архив активности. Флаги `начала нет`, `стопа нет`, `обрезан`, `потеряно записей`.

`diagnostics.json` описывает момент **выгрузки**, а не записи: его `loggingLevel`, `locationSamplesIncluded`, `gitSha` к логу не относятся. Сборку опись берёт из `Log file opened`, координаты считает по строкам `Location sample coordinates`. Сырые архивы через `unzip -p` читай, только если `klog` чего-то не умеет, и никогда не распаковывай в репозиторий.

Готово, когда для каждой активности, о которой спросили, известны `id@дата`, полнота, сессия, сборка (или что она неизвестна) и есть ли в логе координаты.

### 2. Перепись сообщений

```bash
tools/klog/klog.py jq -a 45 -- -r '"\(.category)\t\(.level)\t\(.message)"' | sort | uniq -c | sort -rn
```

Набор сообщений зависит от сборки, которая писала лог (`gitSha` в `Log file opened`). Отсутствие сообщения — сначала вопрос «эта сборка его писала?», и только потом «событие не случилось». Там, где есть `Recording heartbeat`, молчание источника проверяй по его счётчикам, а не по отсутствию строк. Например, старые логи (сессия `b402c71f`) не содержат `Segment detector decision`, `Step counter reading` и `autoMode`.

Признаки порчи (`Activity log truncated`, `droppedRecords`) опись показывает флагами `обрезан` и `потеряно записей`.

Готово, когда перепись есть по каждой активности и отмечены сообщения, которых ждал, но нет.

### 3. Рамка и хронология

```bash
tools/klog/klog.py frame -a 45
```

Рамка собирает в ~20 строк то, что раньше читалось отдельными запросами:

- **Процесс** — `Application started`, `Previous process exit`, восстановление сессии; `[app]` — из общего потока вне записи.
- **Старт** — пороги и настройки, **действовавшие во время записи**. Сравнивай цифры автопаузы с ними, а не с текущим `TrackProcessingConfig`: код с тех пор мог измениться.
- **Окружение на старте** и **по ходу** — снимки `SYSTEM` и сколько раз они менялись.
- **Запрос геолокации**, **Распознавание**, **Сэмплы** (провайдеры, отброшенные, выбросы), **Пульс** (итоги и минуты с нулевым источником), **Автопауза**, **Сегменты** (живые против декодированных), **Стоп**, **WARN/ERROR**.
- **Данные** — вердикт по правилу гайда. `плохие` — дальше иди в `SYSTEM`, а не в алгоритмы. `provider=fused` нормален; плохим считается перевес `network`.

Хронология — время от старта записи (`м:сс`, до старта — с минусом), подряд идущие повторы склеены (`×N`, у чисел диапазон), у тяжёлых сообщений оставлены ключевые поля, события приложения вокруг записи помечены `[app]`:

```bash
tools/klog/klog.py timeline -a 45                          # INFO+, вся запись
tools/klog/klog.py timeline -a 45 --skip recognized        # без потока вердиктов распознавания
tools/klog/klog.py timeline -a 45 --from 2:10 --to 2:40 --level DEBUG   # сэмплы в окне
tools/klog/klog.py timeline -a 45 --grep CONFIRMED         # --grep ищет по всем уровням
tools/klog/klog.py timeline -a 45 --from 9m --to 11m --full             # все поля
```

`DEBUG` без окна не запрашивай — это тысячи строк; вывод и так обрезается на `--limit` (300) с подсказкой.

### 4. Ветка по вопросу

Два инструмента для любой ветки, где спор о цифрах:

```bash
tools/klog/klog.py stats -a 45                   # окна по 5 минут; --by 1m — мельче
tools/klog/klog.py stats -a 45 --by segments     # по декодированным сегментам; live — по живым, marks — по эталонным меткам
tools/klog/klog.py stats -a 41 --ranges 0-1:50=пешком,1:50-17:55=автобус --over 25
tools/klog/klog.py samples -a 45 --from 2:10 --to 2:40      # сэмпл за сэмплом; --coords — с координатами
```

- `stats` — по каждому окну: скорость провайдера p50/p90/max и скорость трека (км/ч), точность, шаг опроса, доля сэмплов в автопаузе, доля `network`, выбросы, шаги в минуту, какую долю времени окна держался каждый вердикт распознавания. `--over 25` — доля 5-секундных эпох декодера с медианой скорости выше 25 км/ч. Последняя строка `всё` — вся запись. Когда пользователь говорит, где на самом деле шёл и где ехал, — это `--ranges`, а не самописный jq.
- `samples` — один сэмпл на строку: вход (`dt`, провайдер, погрешность, `age`, скорость провайдера в м/с), вердикт конвейера (скорость трека, выброс с причиной, `stop`, накопленная дистанция), отброс до конвейера (`REJ:…`) и решение автопаузы по этому сэмплу (`→AUTO_PAUSE`, `held`). Скорости в м/с — в тех же единицах, что пороги автопаузы в рамке. Всегда с окном `--from/--to`.


Разделы гайда, в которые идти:

- **Трек, дистанция, скачки точек** — «Что пишется во время записи трека»: `provider`, `accuracyMeters`, `outlierReason`, `Location sample rejected before processing`, разрывы.
- **Автопауза** — `Automatic recording state changed` и `Auto pause held` рядом с порогами из шага 3, плюс `sampleIntervalMillis` против `stopWindowMillis`.
- **Сегменты / вид движения** — «Сегменты по виду движения» и `docs/auto-activity-segments.md`. `Activity recognized` рядом с `Segment detector decision`, шаги из `Step counter reading`.
- **Распознавание молчит** — «Системные сигналы», абзац «Как читать молчание распознавания»: `recognitionBroadcasts` в пульсе, `Activity recognition broadcast` с `hasResult=false`, `Activity recognition silent`, порядок `updates removed` и `SUBSCRIBED` в `context/app.jsonl`.
- **Крэш, ошибки, умерший процесс** — `WARN`/`ERROR`, `throwable`, тег `UncaughtExceptionHandler`, цепочка событий перед первой ошибкой; `Previous process exit` в `context/app.jsonl` или общем архиве.
- **Дыры и замирания** — `SYSTEM`: Doze, standby bucket, энергосбережение, выключенная геолокация.

### 5. Прогон через текущий код (трек, автопауза, сегменты)

Инструмент калибровки читает ZIP напрямую и прогоняет записанные сырые сэмплы через **текущий** pipeline:

```bash
./gradlew -q :tools:track-calibration:run --args="$PWD/korno-activity-34-c6b7f566.zip --no-sweep"
```

- Путь абсолютный: gradle запускает задачу из каталога модуля.
- Строка `на телефоне: … сейчас: …` — вердикты во время записи против текущего кода. Расхождение показывает, что код менялся после записи.
- В режиме «Авто» печатаются решения детектора и сегменты до и после декодера Витерби.
- Без `--no-sweep` добавляется перебор порогов, как его читать — `docs/track-calibration.md`.
- Нужны координаты — строки `Location sample coordinates` в логе, а не флаг в `diagnostics.json`. Без них остаётся только ручной разбор.

### 6. Вывод

Каждое утверждение опирается на запись из лога: время от старта, `message` и значения полей. Для каждой причины раздели:

- **Данные**: провайдер, погрешность, система задушила.
- **Алгоритм**: пороги, детектор, фильтр. Укажи, воспроизводится ли это на текущем коде (шаг 5).

Готово, когда на вопрос пользователя дан ответ с доказательствами, а всё, что проверить не удалось (сборка не писала сообщение, лог обрезан, нет координат), названо явно.

## Свои запросы: `klog jq`

Когда готовой команды нет, пиши jq поверх `klog jq`, а не поверх `unzip -p`: записи идут одним потоком без дублей и по времени, а ловушки сырого лога уже сняты.

```bash
tools/klog/klog.py jq -a 45 -- -r 'select(.fields.isOutlier) | "\(.at) \(.fields.outlierReason)"'
tools/klog/klog.py jq -a 45 -- -s '[.[] | select(.message == "Location sample received") | .fields.accuracyMeters] | add / length'
```

- `fields` типизированы: числа — числа, `true`/`false` — булевы, `"null"` — `null`. В сыром логе всё это строки.
- `.t` и `.at` — секунды и `м:сс` от старта активности, `.epoch` — секунды UTC, `.src` — `activity` / `app` / `context`.
- С `-a` в поток входят и события приложения без `activityId` в окне −10 мин … +1 мин; без `-a` — весь пул.
- `sampleTimestamp`, `readingTimestamp`, `signalTimestamp`, `boundaryTimestamp` — epoch ms самого события, а не записи в лог. `Location sample received` и `Location sample coordinates` связаны через `sampleTimestamp`.
- Аргументы jq — после `--`.
