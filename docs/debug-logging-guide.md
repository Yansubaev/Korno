# Как читать debug-логи Korno

Логгер работает только в debug-сборке. Откройте **Настройки → Диагностика**, включите логирование и выберите минимальный уровень. Для обычного тестирования достаточно `DEBUG`; `VERBOSE` и запись GPS-точек лучше включать только на время воспроизведения проблемы.

## Как получить логи

1. Воспроизведите проблему на устройстве.
2. Не очищая данные приложения, откройте **Настройки → Диагностика**.
3. Нажмите **Поделиться логами** и сохраните ZIP-архив удобным способом.
4. Распакуйте архив на компьютере.

Внутри находятся:

- `diagnostics.json` — версия приложения, коммит сборки (`gitSha`, `gitDirty`), версия Play Services, модель устройства, версия Android, ID сессии и настройки логгера. Настройки — **на момент выгрузки архива**, а не записи: `loggingLevel: VERBOSE` и `locationSamplesIncluded: true` у архива, выгруженного после переключения настроек, не значат, что в логе есть `VERBOSE`-записи и координаты. Проверять по самим записям — например, есть ли `Location sample coordinates`;
- `logs/*.jsonl` — непосредственно логи. Каждая строка такого файла является отдельным JSON-объектом.

## Два потока: общий и активности

Подробности записи трека — по строке на каждый сэмпл, уровни `DEBUG` и `VERBOSE` — пишутся **только в лог активности**. В общий поток из записи попадают `INFO` и выше: старт и стоп, смены состояния, системные сигналы, пульс, ошибки. Раньше сэмплы шли в оба файла и занимали 95–97 % общего потока, прокручивая его за пару часов; события самого приложения вне записи в нём почти не оставались.

- **Общий поток** (`korno-diagnostics-<sessionId>.zip`) — жизнь приложения: запуски процесса и причины смерти прошлых, прогрев GPS, ошибки, и по записям — только их каркас. Чтобы восстановить подробности записи, берите архив активности.
- **Лог активности** — всё, что писалось, пока шла запись, включая каждый сэмпл.

Каждый файл начинается строкой `Log file opened` (`APP`, тег `DebugLogger`) — чем он записан: `gitSha`, `gitDirty`, `versionName`, `sdkInt`, `playServicesVersion`. `versionName` у всех debug-сборок одинаковый, и сборку определяют только по `gitSha`; `gitDirty=true` значит, что в сборку вошли незакоммиченные правки. Файл активности, продолженный после перезапуска процесса, получает ещё одну такую строку — с новым `sessionId`.

## Логи одной активности

Откройте активность, пролистайте экран вниз до раздела **Диагностика** и нажмите **Поделиться логами активности**. В архиве `korno-activity-<id>-<sessionId>.zip` лежат:

- `diagnostics.json` — как в общем архиве, плюс `activityId`;
- `logs/activity-<id>.jsonl` — лог самой активности;
- `context/app.jsonl` — записи общего потока **без** `activityId` за окно от 10 минут до старта записи до минуты после стопа: запуск процесса, `Previous process exit`, прогрев GPS, снятие зависшей подписки, итог отписки распознавания после стопа. Файла нет, если в окне ничего не нашлось или общий поток его уже прокрутил.

Команды из этого гайда с маской `logs/*.jsonl` читают только лог активности; контекст приложения читается отдельно или склеивается по времени:

```bash
unzip -p korno-activity-19-7f06a43b.zip 'logs/*.jsonl' 'context/*.jsonl' | jq -s 'sort_by(.timestampUtc)[]'
```

Лог активности переживает и ротацию общего потока, и перезапуск приложения. Хранятся логи двадцати последних активностей, не дольше семи дней; удаление активности (в том числе отмена тренировки на экране сохранения) удаляет и её лог.

Размер одного такого файла ограничен 8 МБ. При переполнении запись прекращается, а в файле остаётся строка `Activity log truncated: size limit reached`: начало тренировки — настройки, первые фиксы, разгон GPS — объясняет больше, чем её хвост, и терять его ради последних минут смысла нет.

## Формат записи

Пример одной строки, отформатированной для чтения:

```json
{
  "timestampUtc": "2026-09-06T09:41:12.345Z",
  "uptimeMillis": 184205,
  "level": "INFO",
  "category": "TRACKING",
  "tag": "TrackingSessionCoordinator",
  "message": "Tracking session started",
  "thread": "DefaultDispatcher-worker-2",
  "sessionId": "a1b2c3d4",
  "activityId": 42,
  "fields": {
    "segmentKind": "RUNNING",
    "autoPauseEnabled": "true"
  }
}
```

Основные поля:

- `timestampUtc` — абсолютное время события в UTC, а не в часовом поясе устройства;
- `uptimeMillis` — время с момента загрузки устройства; удобно для оценки интервалов;
- `level` — важность записи: `VERBOSE`, `DEBUG`, `INFO`, `WARN` или `ERROR`;
- `category` — область приложения: `APP`, `TRACKING`, `GPS`, `DATABASE`, `NETWORK`, `EXPORT`, `UI` или `SYSTEM`;
- `tag` — класс или компонент, создавший запись;
- `sessionId` — ID запуска приложения, связывающий записи между файлами;
- `activityId` — активность, во время записи которой сделана запись; поле отсутствует, если запись трека не шла;
- `fields` — дополнительные параметры события;
- `throwable` — stack trace исключения; поле присутствует только при ошибке.

Значение `fields.droppedRecords` означает, что очередь логгера была переполнена и указанное количество предыдущих записей потеряно. Значение `<redacted>` означает, что секретное поле было автоматически скрыто.

## Быстрый анализ

Для удобного просмотра всех записей нужен `jq`:

```bash
jq . logs/*.jsonl
```

Собрать несколько файлов в единую временную последовательность:

```bash
jq -s 'sort_by(.timestampUtc)[]' logs/*.jsonl
```

Показать только предупреждения и ошибки:

```bash
jq -c 'select(.level == "WARN" or .level == "ERROR")' logs/*.jsonl
```

Показать события GPS и трекинга:

```bash
jq -c 'select(.category == "GPS" or .category == "TRACKING")' logs/*.jsonl
```

Разобрать поведение автопаузы:

```bash
jq -c 'select(.message | test("recording state changed|Auto pause held"))' logs/*.jsonl
```

Выбрать из общего архива каркас одной активности — только `INFO` и выше, сэмплы лежат в архиве самой активности:

```bash
jq -c 'select(.activityId == 42)' logs/*.jsonl
```

Посмотреть, что система думала об активности во время записи:

```bash
jq -c 'select(.category == "SYSTEM")' logs/*.jsonl
```

Сводка качества записи одной строкой:

```bash
jq -c 'select(.message == "Tracking session stopped") | .fields' logs/*.jsonl
```

Распределение погрешности и шага опроса — если жалоба на «прыгающий трек»:

```bash
jq -r 'select(.message == "Location sample received")
  | [.fields.provider, .fields.accuracyMeters, .fields.sampleIntervalMillis] | @tsv' logs/*.jsonl
```

Почему точки отбрасывались:

```bash
jq -r 'select(.message == "Track point processed" and .fields.outlierReason != "")
  | .fields.outlierReason' logs/*.jsonl | sort | uniq -c
```

Сетевые фиксы вместо GNSS — самая частая причина и разброса точек, и несработавшей автопаузы:

```bash
jq -r 'select(.message == "Location sample received") | .fields.provider' logs/*.jsonl | sort | uniq -c
```

Найти записи с исключениями:

```bash
jq -r 'select(.throwable != null) | "\(.timestampUtc) [\(.tag)] \(.message)\n\(.throwable)"' logs/*.jsonl
```

Если `jq` недоступен, быстрый текстовый поиск тоже работает:

```bash
rg '"level":"(WARN|ERROR)"|Unhandled exception' logs
```

## Что пишется во время записи трека

Запись трека логируется тремя слоями, и по одному без остальных картину не собрать.

**Вход.** `Location sample received` — каждый сэмпл от провайдера: `accuracyMeters`, `reportedSpeed`, `sampleIntervalMillis` и текущий статус записи. Координат в этой записи нет, она пишется на уровне `DEBUG` всегда. Сами широта и долгота идут отдельной записью `Location sample coordinates` на уровне `VERBOSE` и только при включённой настройке «Включать GPS-точки».

Там же лежат поля, по которым видно происхождение фикса, — без них сетевую точку от GNSS-точки не отличить:

- `provider` — `gps`, `fused` или `network`. Стометровая погрешность вместе с `network` означает, что GNSS-чип в этот момент не работал;
- `ageMillis` — сколько фикс пролежал до того, как дошёл до приложения; Fused Location Provider умеет отдавать кэш, и по времени записи этого не видно;
- `satelliteCount` — число спутников в решении; у сетевых фиксов отсутствует;
- `verticalAccuracyMeters` и `speedAccuracyMetersPerSecond` — есть не у всех провайдеров, но когда есть, сразу показывают, стоит ли верить набору высоты и доплеровской скорости.

**Обработка.** `Track point processed` — вердикт по каждой точке: `isOutlier` (точка признана выбросом), `isStop` (точка попала в остановку), накопленные `distanceMeters` и `movingTimeMillis`. Расхождение между числом сэмплов и приростом дистанции разбирается именно здесь.

У отброшенной точки есть `outlierReason`, иначе отказ выглядит как потерянный сэмпл:

- `ACCURACY` — погрешность хуже `maximumAccuracyMeters`, точка описывает не положение, а круг;
- `SPEED` — перемещение невозможно на этой скорости или с этим ускорением даже с поправкой на погрешность;
- `TIMESTAMP` — время точки не больше времени предыдущей.

Рядом идут `gapCount` и `unmeasuredTimeMillis` — сколько раз трек прерывался и сколько времени в этих разрывах накопилось. Отрезок длиннее минуты не наблюдался: его дистанция засчитывается как нижняя оценка пройденного, но ни в мгновенную, ни в максимальную скорость он не идёт, и на карте рисуется пунктиром.

Накопленная дистанция намеренно отстаёт от последних точек на пару сэмплов: пока сглаживание может сдвинуть точку, засчитывать её рано. Поэтому `distanceMeters` в живой записи только растёт, а окончательное значение появляется в `Tracking session stopped` после полного пересчёта трека. Решение об автопаузе, наоборот, принимается по самой свежей точке и не отстаёт.

**Решения.** `Automatic recording state changed` (смена состояния) и `Auto pause held` (сэмпл пришёл, но пауза сохранилась). Обе несут поля решения: `reportedSpeed` — скорость от провайдера (`null` означает, что её не было, и решение принималось только по координатам), `currentSpeed` — скорость по обработанному треку, `accuracyMeters` — погрешность точки и `sampleIntervalMillis` — шаг с прошлой точки. Последнее поле важнее, чем кажется: детектор остановок рассуждает временными окнами, и если шаг сравним с `stopWindowMillis`, в окно попадает слишком мало точек.

Первой записью лога активности после `Log file opened` идёт `Tracking session started` с настройками, при которых пошла запись: `autoPauseEnabled`, `autoPauseSensitivity`, `gpsAccuracy`, `stopSpeedMetersPerSecond`, `resumeSpeedMetersPerSecond`, `stopWindowMillis`, `minimumStopDurationMillis`, `stopRadiusMeters`, `maximumSpeedMetersPerSecond`, `maximumAccuracyMeters`, параметры фильтра Калмана `processNoiseAcceleration`, `outlierGateChiSquare`, `positionNoiseFloorMeters`, а в новых версиях ещё `autoMode` — включено ли автоопределение вида движения. Без них цифры автопаузы не с чем сравнивать. Та же строка появляется и после восстановления сессии — `Active tracking session recovered`.

Настройка точности GPS попадает именно сюда, хотя запросом к провайдеру владеет сервис: подписка на геолокацию поднимается ещё на прогреве, до появления `activityId`, и первая запись `Location update policy changed` уходит только в общий лог — в архиве активности она лежит в `context/app.jsonl`. Повторные смены политики по ходу записи есть и в логе активности.

`Location sample rejected before processing` (`GPS`) — сэмпл выброшен ещё до конвейера и в `Track point processed` не появится. Причина в `rejectedBecause`: `DUPLICATE` — тот же фикс пришёл повторно, `STALE` — фикс слишком старый (`ageMillis`), `PROVIDER` — сетевой фикс.

**Пульс.** `Recording heartbeat` (`TRACKING`, `INFO`) — раз в минуту и ещё раз прямо перед стопом. Счётчики входящих потоков за прошедшую минуту и итоги с начала записи (суффикс `Total`): `locationSamples`, `recognitionBroadcasts` (всё, что пришло от распознавания), `recognitionResults` (из них с вердиктом), `stepReadings`, а также `deviceIdleMode` на момент строки. Молчащий источник виден здесь нулём, а не отсутствием строк; последний пульс перед `Tracking session stopped` — итоги всей записи. Пульс идёт и в общий поток, так что каркас записи виден и там.

Последней записью идёт `Tracking session stopped` со сводкой качества записи — с неё удобно начинать разбор, не читая сотни строк про отдельные сэмплы:

- `outlierCount` и `stopPointCount` — сколько точек отброшено и сколько попало в остановки;
- `accuracyMedianMeters` и `accuracyP90Meters` — с какой точностью вообще шла запись;
- `sampleIntervalMedianMillis` и `sampleIntervalP90Millis` — реальный шаг опроса против запрошенного в `Location update policy changed`. Расхождение медианы с запрошенным интервалом означает, что провайдер запрос не отрабатывал;
- `gapCount`, `unmeasuredTimeMillis` и `unmeasuredTimeShare` — сколько раз трек прерывался и какая доля активности пришлась на разрывы. Доля выше 0.2 означает, что обрабатывать было почти нечего, и вопросы к алгоритмам можно не задавать.

## Сегменты по виду движения

Пишутся, когда запись идёт в режиме «Авто» (`autoMode=true`), подробности фичи — `docs/auto-activity-segments.md`.

- `Step counter reading` — `stepCounter` (накопительный счётчик с загрузки устройства), `readingTimestamp` (момент показания по сенсору, `SensorEvent.timestamp`) и `deliveredAt` (когда показание дошло до приложения); не чаще раза в интервал, для любого типа активности. Большая разница `deliveredAt − readingTimestamp` — показания пришли пачкой, так бывает в doze. В логах до появления `deliveredAt` в `readingTimestamp` лежит время доставки.
- `Segment detector decision` — каждое решение живого детектора, поле `decision`: `CANDIDATE` (`kind`), `DROPPED` (кандидат не удержался), `REJECTED` (вердикт распознавания отклонён, `reason`: `LOW_CONFIDENCE`, `NOT_MOVEMENT`, `SPEED`, `MANUAL_HOLD`, `PAUSED`) и `CONFIRMED` (`from` → `to`, `boundaryTimestamp`, `manual`). `CONFIRMED` пишется на `INFO`, остальные — на `DEBUG`.
- `Ground truth mark` — эталонная метка (`INFO`): человек нажал дебажную кнопку-флажок на экране записи и выбрал, как движется на самом деле. Поля `kind` (`ON_FOOT`, `RUNNING`, `CYCLING`, `VEHICLE`) и `markTimestamp`. На сессию, сегменты и декодер не влияет; `:tools:track-calibration` считает по меткам, насколько разметка совпала с эталоном. Кнопка есть только в debug-сборке и только в авторежиме.
- `Activity mode decoded` — одна запись при остановке: `liveSegments` (что нарезал живой детектор) против `decodedSegments` (что пересчитал декодер Витерби по всей записи и что будет сохранено). Формат `KIND@м:сс-м:сс` от начала записи. Расхождение этих двух строк — первое, на что смотреть при жалобе на сегменты.

## Системные сигналы

Категория `SYSTEM` — то, что происходит вокруг приложения и способно объяснить поведение трека. Эти подписки включаются только под запись трека и только при включённом логировании, потому что стоят батареи.

- `Activity recognized` — что о происходящем думает система: `detectedActivity` (`WALKING`, `RUNNING`, `ON_FOOT`, `ON_BICYCLE`, `IN_VEHICLE`, `STILL`, `TILTING`, `UNKNOWN`), `confidencePercent` и `alternatives` с прочими вариантами. Записывается только смена вердикта. Расхождение с выбранным типом активности объясняет и «слишком быстрый» трек, и остановки, которых пользователь не делал. Требует разрешения на распознавание активности; без него сигналов просто не будет.

  `ON_FOOT` — не отдельный вариант, а зонтик над `WALKING` и `RUNNING`, и Play Services почти всегда ставит его первым. В вердикт он попадает только тогда, когда конкретного варианта рядом нет; в остальных случаях его видно в `alternatives`.
- `Activity recognition subscription` — чем кончилась подписка на распознавание, одна запись в начале: `status` = `SUBSCRIBED` (Play Services принял) или `NO_PERMISSION` (подписываться не стали), `subscription` — номер подписки в процессе. Отказ Play Services пишется как `ERROR` `Activity recognition stream failed` с `throwable`. В логах, записанных до появления этой строки, её нет вовсе.
- `Activity recognition broadcast` — каждый пришедший от Play Services интент, раз в несколько секунд: `hasResult`, `action`, `extras` (ключи), `resultAgeMillis` (сколько вердикт шёл до приложения), `subscription`. С результатом — `DEBUG`, **без результата — `WARN`**: интент пришёл, но вердикта в нём нет, и `Activity recognized` за ним не будет. `Activity recognized` пишется только при смене вердикта, broadcast — всегда.
- `Activity recognition silent` (`WARN`) — за 60 секунд после подписки не пришло ни одного broadcast. Одна строка на подписку.
- `Activity recognition updates removed` / `Activity recognition removal failed` — итог отписки при остановке записи, с `broadcastCount` за всю подписку. Приходит асинхронно, обычно уже после стопа, поэтому лежит в общем потоке, в архиве активности — в `context/app.jsonl`.
- `Stale activity recognition subscription removed` — только в общем логе, при старте процесса: от прошлого процесса, убитого посреди записи, осталась подписка на распознавание, и она снята. Нет строки — снимать было нечего. Отказ Play Services снять её — `WARN` `Stale activity recognition removal failed`.

  Как читать молчание распознавания: `SUBSCRIBED` есть, а в пульсе `recognitionBroadcasts=0` — Play Services ничего не шлёт (смотреть `playServicesVersion` в `Log file opened` и `dumpsys` на телефоне); broadcast'ы есть, но с `hasResult=false` — вердикт приходит в виде, который приложение не разбирает; `updates removed` соседней подписки позже `SUBSCRIBED` следующей — регистрацию сняли мы сами.
- `Permissions snapshot` — снимок разрешений при старте записи: `preciseLocation`, `approximateLocation`, `backgroundLocation`, `activityRecognition`, `notifications`. `approximateLocation=true` при `preciseLocation=false` — пользователь дал только приблизительную геолокацию, и трек строится по кругам в километр.
- `Device idle mode changed` — `deviceIdleMode` и `ignoringBatteryOptimizations`. Doze — единственное состояние, которое одновременно режет и геолокацию, и распознавание активности: если оба источника замолчали разом, смотреть надо сюда. Приложение из белого списка переносит Doze заметно мягче.
- `Background restriction changed` — `backgroundRestricted` и `standbyBucket` (`ACTIVE`, `WORKING_SET`, `FREQUENT`, `RARE`, `RESTRICTED`). Снимок пишется при старте записи и объясняет, почему сервис получает точки реже, чем просит, ещё до всякого Doze.
- `Location providers changed` — `gpsEnabled` и `networkEnabled`. Самая частая причина дыры в треке: геолокацию выключили посреди записи.
- `Power save mode changed` — режим энергосбережения режет частоту обновлений независимо от настроек приложения.
- `Screen state changed` — с момента гашения экрана начинают действовать ограничения на фоновую работу.
- `Battery state changed` — заряд с шагом в 5 % и факт зарядки.

Провайдеры геолокации, энергосбережение, экран, Doze, фоновые ограничения и разрешения пишутся снимком сразу при старте записи: иначе нельзя отличить «энергосбережение включили в середине пробежки» от «оно было включено с самого начала».

## Процесс приложения

- `Application started` — старт процесса.
- `Previous process exit` — сразу за ним, почему умер прошлый процесс (Android 11+): `reason` (`USER_REQUESTED` — смахнули из недавних или остановили в настройках, `CRASH`, `CRASH_NATIVE`, `ANR`, `LOW_MEMORY`, `FREEZER`, `PACKAGE_UPDATED` — установили новую сборку, и другие), `description`, `status`, `importance` (100 — на экране, 125 — foreground-сервис, 400 и выше — кэш) и `exitTimestamp` (epoch ms). Крэш, который логгер не успел сбросить на диск, виден только здесь.

## На что смотреть при расследовании

Начните с `diagnostics.json`, затем найдите нужный `sessionId` и время воспроизведения. Просматривайте цепочку событий перед первым `WARN` или `ERROR`, а при проблемах записи маршрута фильтруйте категории `TRACKING` и `GPS`. Необработанный краш помечается тегом `UncaughtExceptionHandler` и содержит stack trace в `throwable`.

С жалобами на трек порядок другой и почти всегда один и тот же: сперва `Tracking session stopped` — там вся статистика качества сразу, — и только потом отдельные точки. Если `accuracyMedianMeters` за два десятка метров, `sampleIntervalMedianMillis` заметно больше запрошенного, а `provider` у половины сэмплов не `gps`, то дело не в обработке трека: записи просто не из чего было его построить. Тогда смотреть надо в `SYSTEM` — на `Device idle mode changed`, `Background restriction changed` и `Power save mode changed`.

Логи хранятся во внутреннем хранилище приложения: общий поток — максимум пять файлов по 2 МБ, логи активностей — двадцать последних, и всё это не дольше семи дней. Очистка данных или удаление приложения удаляет их. Точные GPS-координаты попадают в файл только после отдельного включения этой настройки, поэтому перед передачей архива проверьте, допустимо ли раскрывать маршрут.
