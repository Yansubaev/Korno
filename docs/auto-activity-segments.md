# Автоопределение вида движения и сегменты активности

Одна запись может состоять из участков разного вида движения: поехал на велосипеде,
спешился и повёл его в гору; доехал на автобусе и дошёл пешком. Раньше вся запись
обрабатывалась одним видом: спешивание на велосипеде выглядело как медленная
езда и портило статистику, а шаги считались только для пеших видов.

Фича разбивает запись на **сегменты** по виду движения, определяет вид автоматически во
время записи и показывает, сколько пройдено, сколько проехано и на чём.

## Режимы записи

При старте пользователь выбирает режим:

- **Авто** — вид движения определяет детектор, запись режется на сегменты;
- **Фиксированный вид** — один сегмент, детектор выключен, шаги считаются только для
  пеших видов (`SegmentKind.countsSteps`).

Последний выбор запоминается; при первом запуске — «Авто».

«Авто» доступен только при выданном `ACTIVITY_RECOGNITION` и работающих Play Services.
Иначе при выборе «Авто» предлагается выдать разрешение, а без него остаётся только
фиксированный режим. Эвристику по одной скорости не делаем: без разрешения нет и
шагомера, а скорость путает медленный велосипед с бегом — ровно тот случай, ради
которого фича.

## Модель данных

### Вид сегмента

`SegmentKind` — единственное понятие о том, чем человек передвигался: `ON_FOOT`,
`RUNNING`, `CYCLING`, `VEHICLE`, `HIKING`, `UNKNOWN`, `PAUSE` (см. `ADR 0004`). Своего
вида у активности нет — за неё говорит доминирующий.

Датчики выдают не весь перечень: хайкинг от прогулки они не отличают, и `HIKING` ставит
только человек — на всю запись сразу (`ADR 0005`). `UNKNOWN` детектор тоже не выдаёт; он
входит в общую статистику, но не показывается в разбивке по видам.

### Таблица `activity_segments`

| Колонка | Смысл |
|---|---|
| `id` | PK |
| `activity_id` | FK на `activities`, `ON DELETE CASCADE` |
| `kind` | `SegmentKind` |
| `start_ts` | начало сегмента |
| `end_ts` | конец; `null` у открытого сегмента во время записи |
| `steps` | дельта `TYPE_STEP_COUNTER` за сегмент, `null` — шаги не считались |
| `distance_meters` | дистанция сегмента после обработки |
| `is_manually_edited` | вид изменён пользователем |

Точки привязываются к сегменту по времени, отдельной колонки в `geo_points` нет.

Сегмент пишется в БД в момент подтверждения границы (закрыть старый + вставить новый).
При восстановлении сессии после смерти процесса открытый сегмент продолжается.

### Миграция

Room 5 → 6: создать таблицу и SQL-ом вставить каждой существующей активности один
сегмент на всю длительность с видом из тогдашнего типа активности и `steps = step_count`.
Код чтения всегда работает с сегментами, без ветки «сегментов нет».

### Лицо активности

Иконка, подпись, темп или скорость и вид спорта при экспорте берутся из доминирующего по
дистанции вида сегментов. Отдельного поля у активности для этого нет (`ADR 0004`).

## Детектор

### Сигналы

- Activity Recognition (Play Services) — основной источник. Подписка уже есть в
  `ActivityRecognitionSignalSource`, сейчас только для диагностического лога; в
  авторежиме она работает всегда, вместе с логикой выбора конкретного варианта вместо
  зонтика `ON_FOOT`.
- Каденс шагов за скользящее окно (`TYPE_STEP_COUNTER`).
- Скорость после Kalman-фильтра.

### Правила

- Детектор — **чистая функция** над потоком сигналов: состояние + сигнал → состояние +
  решение. Без Android-зависимостей, покрыт unit-тестами.
- **Гистерезис**: смена вида засчитывается, только если новый вердикт держится
  `confirmWindow` (стартовое значение 30–45 с). Граница сегмента ставится **задним
  числом** на момент первого признака, а не на момент подтверждения.
- **STILL не сегмент**: остановки — работа автопаузы, текущий сегмент не рвётся.
- После ручной паузы окно гистерезиса начинается заново, вердикты за время паузы не
  учитываются.
- **Ручная поправка**: пользователь меняет вид текущего сегмента, граница — «сейчас».
  После этого детектор `manualOverrideHold` (≈2 мин) игнорирует противоречащие вердикты.
- При сохранении сегменты короче `minSegmentDuration` (1 мин) или `minSegmentDistance`
  (50 м) сливаются с соседом.
- Все пороги — в одном конфиге детектора.

### Итоговая разметка при сохранении — декодер

Живой детектор решает, не зная будущего, и верит распознаванию: в записи 31 он записал
полторы минуты «машины» посреди велопоездки. Поэтому при сохранении вид всей записи
заново определяет `ActivityModeDecoder` — скрытая марковская модель, декодируемая
алгоритмом Витерби. Живые сегменты остаются только для экрана записи и как запасной
вариант, если распознавание ничего не сказало о движении.

- Время режется на эпохи по 5 с; скрытое состояние эпохи — `ON_FOOT`, `RUNNING`,
  `CYCLING` или `VEHICLE`.
- Наблюдения: ответ Activity Recognition целиком, с альтернативами (таблица
  `recognition_samples`, пишется всю запись); доплеровская скорость; каденс — ходьба
  против бега.
- Ответ распознавания считается наблюдением, только если он о движении. Своё незнание
  Play Services выражает вердиктом `UNKNOWN` с ровными `IN_VEHICLE=10, ON_BICYCLE=10,
  ON_FOOT=10`, и альтернативы в нём есть: считать их голосом — значит топить пешие виды
  и ставить велосипед с транспортом в ничью, которую разрешит уже не улика, а штраф
  пересадки. На записях 41 и 46 такой ответ занимал 77 % и 65 % времени.
- В эпохе держится последний ответ **о движении**. Play Services отдаёт `IN_VEHICLE` и
  следом `STILL` в ту же секунду (транспорт встал), и последний-по-времени стирал
  вердикт, ради которого весь разбор: в записи 46 так пропали четыре из пяти.
- Скорость работает двумя способами. Физический предел (пешком не быстрее 3 м/с, бегом
  7, на велосипеде 25) говорит, что вид невозможен. Отдельно от него крейсерская
  скорость велосипеда (8.3 м/с ≈ 30 км/ч) отличает велосипед от транспорта, чего предел
  не умеет: в городе они ездят одинаково и расходятся только на верхнем конце. Эпоха
  быстрее — сильный голос за транспорт, эпоха едущая, но медленная — слабый против него.
  Замеры по записям 41/45/46: автобус и машина проводят выше 30 км/ч 15–20 % эпох и
  разгоняются до 44–50, велопоездка — ни одной эпохи при максимуме 26.8.
- Переходы: любая смена вида стоит штрафа, а смена с транспортом или на транспорт —
  ещё и большого штрафа пересадки, который снимает остановка ≥ 20 с, пропуск GPS
  ≥ 30 с или ручная пауза. Сесть в машину или слезть с неё на ходу нельзя, поэтому
  «машина» без остановок на концах проигрывает, а граница настоящей пересадки сама
  встаёт на остановку, даже если распознавание заметило смену позже. Остановка ищется
  как заезд ниже 2 м/с, внутри которого нашлась точка в покое: у стоящего приёмника
  доплер шумит на 0.4–1.3 м/с, и требование покоя от каждой точки рассыпало настоящую
  остановку автобуса на одиночки (запись 41, 17:54–18:06).
- Ручные поправки пользователя декодер не оспаривает.
- После декодера короткие сегменты сливаются так же, как раньше.

Решение декодера пишется в лог (`Activity mode decoded`) рядом с живыми сегментами.

### Проверка и калибровка

Документации верим оптимистично, но механизм должен проверяться на реальных записях:

- решения детектора (вердикт, уверенность, подтверждение, отклонение, граница) и дельты
  шагов по **всем** сегментам пишутся в диагностический лог;
- `:tools:track-calibration` получает прогон детектора по архивам логов
  (`LogTrackReader` уже читает архивы) со сводкой сегментов и перебором порогов
  детектора — так же, как для `TrackProcessingConfig`.

Отдельно стоит проверить гипотезу, что при педалировании с телефоном в кармане шорт
шагомер считает шаги: шаги `CYCLING`-сегментов хранятся именно для этого.

## Пороги трека в смешанной записи

Сейчас `TrackProcessingConfig` выбирается по типу активности на всю запись. С пешими
5.5 м/с фильтр выбросов выкинет все точки автобуса, и детектор ослепнет по скорости.

- Во время записи профиль порогов (выбросы, автопауза, Kalman) переключается вместе с
  текущим сегментом.
- До первого подтверждённого вердикта действует самый терпимый профиль — `VEHICLE`.
- Состояние Kalman при смене сегмента не сбрасывается (траектория непрерывна), меняется
  только профиль.
- Постобработка при сохранении и после смены вида сегмента пользователем применяет
  пороги по сегментам.

## Шаги

- В авторежиме шагомер работает всю запись, дельта пишется в каждый сегмент.
- В сводке показываются только шаги `ON_FOOT` и `RUNNING`; шаги `CYCLING`/`VEHICLE`
  хранятся, но не показываются.
- Фиксированный режим — как сейчас.

## UI

### Экран записи (авторежим)

- Чип текущего вида; тап по нему — ручная поправка.
- Главная метрика по текущему виду: темп для `ON_FOOT`/`RUNNING`, скорость для
  `CYCLING`/`VEHICLE`.
- Строка разбивки дистанции по встреченным видам: «🚶 1.2 км · 🚲 8.4 км · 🚌 3.0 км».
- В уведомлении сервиса — иконка текущего вида.

### Экран итога

- Выведенный тип активности с возможностью поменять.

### Экран деталей

- Полилиния окрашена по виду сегмента, легенда — только встреченные виды.
- Сводка: общая дистанция и время + разбивка по видам (дистанция, время, темп/скорость,
  шаги у пеших). `VEHICLE` показывается отдельно и **не входит** в общие темп и скорость.
- Сплиты и insights (`AnalyzeTrackUseCase`) считаются по точкам доминирующего вида.
- Список сегментов; тап — смена вида с пересчётом статистики.

## Вне скоупа

- Перетаскивание границ сегментов на карте — когда смены вида окажется мало.
- Сплиты по каждому виду — когда появятся записи с сопоставимыми по длине видами.
- Сегменты в GPX (`<trkseg>` + extensions) — когда понадобится обратный импорт своих
  GPX. Экспорт не меняется.
- Эвристика без Activity Recognition.
- Автоопределение хайкинга по местности.
- Изменения в списке активностей.

## Этапы

Каждый этап — отдельный мёрж, после которого приложение работает.

### 1. Модель сегментов

- `SegmentKind`, доменная модель сегмента, `ActivitySegmentEntity`, DAO, мапперы.
- Миграция 5 → 6 с заполнением по существующим активностям + тест миграции.
- Фиксированный режим пишет один сегмент на запись (открыть на старте, закрыть на
  остановке, восстановить после рестарта). Шаги пишутся и в сегмент.

Видимых изменений нет; данные для всех новых и старых записей уже в сегментах.

### 2. Детектор и калибровка

- Чистый детектор с конфигом и unit-тестами на правила (гистерезис, граница задним
  числом, STILL, ручная поправка, пауза, слияние коротких).
- Прогон детектора по архивам логов в `:tools:track-calibration`.
- В диагностический лог — шаги для всех типов активности (поток шагомера открывается
  всегда при логировании), чтобы уже с этого этапа копить записи велопоездок.

Видимых изменений нет; детектор можно гонять по логам.

### 3. Авторежим в сервисе записи

- Режим записи в `RecordingSession`; подписка на Activity Recognition и шагомер в
  авторежиме.
- Детектор в `TrackingSessionCoordinator`: сегменты в БД на подтверждении, восстановление
  открытого сегмента, решения — в диагностический лог.
- Переключение профиля порогов трека по текущему сегменту, стартовый профиль `VEHICLE`.
- Шаги по сегментам.

Включается временным флагом (например, в debug-настройках) — можно ездить и проверять
до появления UI.

### 4. Старт и экран записи

- Выбор «Авто / тип» при старте, запоминание, проверка разрешения.
- Чип текущего вида с ручной поправкой, метрика по виду, строка разбивки.
- Иконка вида в уведомлении.
- Флаг из этапа 3 убирается.

### 5. Сохранение и итог

- Слияние коротких сегментов, постобработка с порогами по сегментам, `distance_meters`
  по сегментам.
- Лицо активности — доминирующий вид, правка вида на экране активности.
- Статистика активности без `VEHICLE` в темпе и скорости.

### 6. Экран деталей

- Окраска полилинии по видам и легенда.
- Разбивка по видам, шаги только пеших.
- Сплиты и insights по доминирующему виду.
- Список сегментов со сменой вида и пересчётом статистики.

### 7. Калибровка по реальным записям

- Несколько записей: велосипед (телефон в кармане шорт, в рюкзаке, на руле) со
  спешиванием, автобус + пешком, бег с остановками.
- Прогон через `:tools:track-calibration`, подстройка конфига детектора.
- Вывод по шагам при педалировании; если шаги шумят — не использовать каденс как
  сигнал в `CYCLING`.
